# Schema freeze review

Written 2026-11-20, as the M9 "schema freeze review" task. **Status: waiting for decisions** (see the end). Nothing in the code has changed because of this review, apart from the golden tests described in section 7.

## What "frozen" means

Below 1.0.0 a breaking change to a format bumps the minor version (rule 1 in `CLAUDE.local.md`). At 1.0.0 the settings schema is frozen:

- **Allowed without a new settings version:** adding an optional key, adding an option to an enumerated key, widening a numeric range, adding a preset, adding an optional field to a layout. Older files and links read back exactly as before.
- **Needs a new settings version and a migration:** renaming or removing a key, removing an option, narrowing a range, changing a default, changing what a key means, changing what a preset sets.

A saved settings file, a layout, a share link or a presets file made today must still open, and look the same, after 1.0. This review looks for anything we would regret being unable to change then.

## How to read this

Each finding has an id, what it is today, what could go wrong, the options, and my recommendation. The decisions I need from you are collected in section 8. I did not look at anything the product does not expose.

## 1. The settings schema: names and values

The schema has 32 keys plus `version`, in five groups (Loader 14, Image 5, Text 3, Timing 7, Colors 3). It is one flat object; the typed table in `packages/core/src/schema/ranges.ts` is the only source, and the types, defaults, validation, JSON Schema and the docs' reference page are all derived from it.

## 2. Versions

| Id  | Area                                                                                                                                                                                          | Today                                                                                                  | Risk                                                                                                                                                                            | Recommendation                                                                                                                                                                                                             |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V1  | `parseSettings` and `parseLayout` **ignore the input's `version`**. Verified: `parseSettings({ version: 2 })` returns a version 1 object with no notice. The output always says `version: 1`. | A file from a future version would be read as version 1, with its unknown keys dropped and no warning. | After a version 2 exists, an old Veilo opening a new file would silently show something different. The share link and presets file already detect "newer", the settings do not. | **Add detection before the freeze** (decision D3): `parseSettings` stays lenient, but reports a newer version so the caller can say "made with a newer version of Veilo". The result gets one optional field.              |
| V2  | There is **no migration code**. `migrate.ts` was kept out until it has content.                                                                                                               | Correct for now: there is only version 1.                                                              | The first breaking change needs the whole path at once: detect the version, migrate step by step, then validate.                                                                | **Write the policy now, the code when needed.** The stability page states the rule (a migration for every version step, with the old file kept as a golden test), and the golden tests below are what it will run against. |
| V3  | The published JSON Schema says `additionalProperties: false` and `version: const 1`, while the parser accepts anything and ignores unknown keys.                                              | Strict for tools such as editors, lenient at runtime, on purpose.                                      | When version 2 exists, `const 1` is wrong.                                                                                                                                      | **Keep the behavior, document the difference,** and change `version` to a numeric range when the first new version ships.                                                                                                  |
| V4  | The layout format has its own `version` (1), also ignored on input. It accepts unknown top-level keys, which is what lets the Skeleton builder (M10) add a `builder` field later.             | `parseLayout` returns version 1 whatever it read.                                                      | Same as V1.                                                                                                                                                                     | **Same fix as V1,** in the same change.                                                                                                                                                                                    |

## 3. Flat or grouped

The specification sketches `createReveal(container, { image: {}, text: {}, duration, easing })`. The product built the flat object everywhere: the playground store, share links, saved presets, the JSON Schema, every wrapper's `settings` prop and the presets. Mapping between the two was left as an open decision in the core README.

**Recommendation (decision D1): close it as flat.** A grouped form can still be added later as an alternative input that maps onto the flat object (it would be additive), so nothing is lost by freezing the flat one. Remove the "open decision" sentence from the core README when this is decided.

## 4. Possible gaps

Things users may ask for. All of them are optional keys, so none blocks the freeze, and adding them after 1.0 is allowed. I list them so that leaving them out is a decision, not an oversight.

- A **seed** for the scramble and the random grid origin. It is fixed at 7 today, for repeatable frames.
- A **repeat count** for the loader. `repeat` is `loop` or `once`.
- **Text timing**: the per-element window (0.55 of the timeline) and the end (0.85) are constants, not settings.
- A **stagger** for the text, separate from the loader's.
- Options that are deliberately **not** settings: `fontFamily`, `ink`, `reducedMotion` and the slot layout. They stay options and layouts.

**Recommendation: add none now.**

## 6. What the freeze does not cover

- The playground's own interface, the website and the docs.
- The pixel output of an effect across browsers and operating systems: it is exact for a given browser, and tested in Chromium.
- The text of messages and warnings.
- Packages marked private (`@veilo-ui/ui`).

## 7. What guards the freeze now

Added with this review, as tests only:

- **`packages/core/test/golden/`.** `settings-v1.frozen.json` is a copy of the table as it is today. The test checks that every key still exists with the same kind and default, that no numeric range was narrowed and no option removed, and that the defaults are unchanged. `settings-v1.full.json` is a settings object with every key set, which must read back unchanged; `settings-v1.lenient.json` pins how bad input is handled (clamping, dropped keys, wrong types, `__proto__`); `layout-v1.json` pins the same for layouts.
- **`apps/website/test/playground/share/golden/`.** A real share link with every setting, one with a few settings and some content, and a presets file with usable and unusable entries.

I checked that the core tests fail when a default is changed or a range narrowed. They are copies, not generated: they may only be edited when a new version of the format is introduced on purpose.
